## Signer interoperability: raw Ed25519/DSSE branch

Use this branch only if the selected signer explicitly supports the exact profile. Prepare two independently controlled **disposable test keys** on the selected devices or service after authorization. Do not use a production owner key. Record only public information: model, firmware, adapter version, public SPKI, SHA-256 fingerprint, input type, payload, expected PAE length/hash, public signatures, results and reviewer. Never retain PINs, private keys, recovery secrets or access tokens. Public metadata can identify a test device or person; apply the agreed evidence-access policy.

1. Construct fixed, bounded, fully valid fixture metadata for the current verifier being qualified: use the documented fixture-policy root or policy payload and payload type for owner administration, or the M3c in-toto statement and payload type for a separate artifact-signing profile. Include synthetic scope, expected fixture state and any required fixture policy and checkpoint; do not use a real release statement. Separately compute `PAE(type, payload)` per [DSSE](https://github.com/secure-systems-lab/dsse/blob/master/protocol.md); record the exact payload bytes, payload type and PAE byte length/hash. Lengths are byte lengths, not character counts.
2. Verify the signer accepts those **exact PAE bytes** and returns the specified raw 64-byte Ed25519 signature; export the corresponding canonical DER SubjectPublicKeyInfo and compute its fingerprint. Verify each signature with a separately implemented or independently maintained Ed25519 verifier against the same public bytes. Use a separately approved test harness to feed complete fixture inputs through `applyFixturePolicyTransition` from `@governanator/fixture-policy` (including two owner signatures) or `verifyFixtureAttestations` from `@governanator/fixture-attestation`, as applicable. The existing `tests/fixture-policy-fixtures.ts` and `tests/fixture-attestation-fixtures.ts` illustrate the input structures but use software keys; a device harness does not yet exist. Independently check the full verifier's canonical SPKI and fingerprint validation as well as low-level signature validity. If the device requires pre-hashing, a different encoding, or an unsupported key algorithm, mark this branch unavailable; do not silently change the signed input.
3. Require the applicable full verifier and independent byte verifier to reject wrong-key signatures and modified payload/type/signature. Exercise swapped signer/identity, malformed or truncated signature and invalid public key/encoding against the full verifier. An unavailable or interrupted signer is an operational `unavailable` result, not a verifier rejection. Verify repeated keys or actor IDs do not count as two owners in the policy test. Separately drill the operational control intended to prevent one person controlling both credentials; if that control cannot establish independence, record person-level independence as unproven.
4. Qualify claimed hardware custody and user-presence/verification separately using the chosen device's documented mechanism and observed authorized test procedure. Verify non-exportability and PIN/touch behavior only to the extent the chosen mechanism can actually establish them. A valid signature alone establishes neither hardware origin nor that two different humans acted.
5. Record `pass`, `fail` or `unavailable` for each assertion and have an independent reviewer check the public test record. Do not advance to a real policy root or release gate based on the signer test alone.

### Security-key assertion branch

For FIDO2/WebAuthn or OpenSSH security-key signing, do not extract a signature field and pass it to the raw DSSE verifier. A separately designed and approved profile must validate the complete signed context, relying-party/origin or SSH application, challenge binding, user-presence/user-verification flags and any required counter behavior. Test its own positive and negative cases against the selected device. Record this branch as unavailable until both the full verifier and real-device interoperability are independently qualified. Relevant specifications: [WebAuthn](https://www.w3.org/TR/webauthn-3/) and [OpenSSH security-key protocol](https://github.com/openssh/openssh-portable/blob/master/PROTOCOL.u2f).

## Checkpoint, witness and freshness qualification

First select and threat-model the real store, independent witness and authenticated time/freshness source. Name their separate administrators and failure domains, bootstrap roots, access controls, retention, allowed update ordering and maximum freshness age. A single local file and the same host's clock cannot establish resistance to rollback of that host. Specify how witness and store updates reconcile when either advances alone; an ambiguous or unauthenticated outcome fails closed.

With separately authorized disposable state and test identities, exercise the **actual selected components**, not just the M3d in-memory model:

1. Establish the test root/checkpoint out of band; record policy/root IDs, digests, epoch, version, witnessed time and public audit references. Verify wrong scope, unknown owners, one owner, duplicate owner/key and unapproved threshold reduction cannot advance it.
2. Race two updates from the same expected version: at most one succeeds. Interrupt before and after each store and witness write, in both possible partial-advance directions; prove reconciliation never grants authority from an uncertain state.
3. Restore a same-epoch old store or backup while the witness remains current; reject it. Exercise same-version/different-digest equivocation, missing or invalid witness, cross-epoch challenge replay, stale/reused challenge and inconsistent consumed-challenge records.
4. Exercise unavailable, stale, future, divergent and rolled-back clock/freshness observations. Verify a locally valid, unexpired but no-longer-current policy cannot silently pass when the authenticated freshness requirement is unmet. State explicitly the bounded freshness claim; do not claim global latestness.
5. Suspend an owner, remove a role and simulate a compromised/lost root; verify fail-closed behavior. Rebootstrap only through the independently authorized test recovery channel with a new witnessed epoch and time floor. Test lost store, stale backup and missing recovery witness. Preserve audit evidence, never secrets.
6. Rotate a root only with both valid old and new owner thresholds over the same successor; confirm the valid transition is accepted and stale, candidate-selected, under-threshold, duplicate-owner and unauthorized roots are rejected. Test that unavailable recovery authority freezes the affected operation.

No fixture result can establish that a real witness is independently controlled, a backend survives hostile rollback, or a clock is trustworthy. Mark each result by environment: fixture, local disposable backend, real test device, hosted test, authenticated GitHub read or registry observation. Do not promote evidence between environments.

## GitHub and artifact gates after signer/state qualification

After separate repository and access authorization, qualify authenticated human-to-stable-GitHub-ID-to-key binding with a single-use scoped proof of possession. Verify source-review identity, current repo/PR/head, dismissal and pagination behavior independently; an installation credential identifies an app, not the enrolling human. The actor's separate exact-artifact statement must bind the source review and all expected release scope, including package/version, baseline, artifact and input digests, policy IDs/digests, creation time and classification. Revalidate applicable reviewer roles, head, policy freshness and exact bytes at a protected decision and publisher handoff. A list of reviews or a local digest alone does not prove that a published artifact was approved.

For the eventual authorized test, use disposable identities and candidates. First demonstrate a correctly scoped, authenticated source review and separately signed exact-artifact fixture as the positive case under the selected test policy; it grants no production authority. Then require rejection or insufficient evidence for a different account, key, challenge or reviewer; reused challenge; missing, partial, stale, superseded or dismissed review; incorrect repository, PR or head; and wrong package, version, baseline, input, policy, classification, role or artifact digest. Test that candidate-controlled verifier code or expected scope is not accepted as independently protected. Alter the test artifact and change review, head or policy between decision and handoff; the protected process must revalidate and reject or report insufficient evidence rather than use the old result. Retain evidence for the actual environment tested, including any unavailable provider or race condition.

Publication, hosted workflow activation, real owner enrollment and the normal release gate each require separate decisions and qualification. This protocol does not make or enable those decisions.
