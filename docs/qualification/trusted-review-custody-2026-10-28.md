## Recommended next trust design

Use the two user-identified people as **candidate** owner principals only after independently authenticating each provider identity and confirming separate control of their software signing keys. Keep each private key with its owner; do not copy it into the repository, logs, or a shared release process. Qualify key enrollment, signature format, revocation and recovery using disposable test keys before enrolling real ones. Software keys do not prove a distinct human, key non-exportability or hardware presence. The existing Ed25519/DSSE fixture verifier must not be treated as a production identity verifier.

Use a protected, versioned checkpoint store with atomic conditional updates for policy state, plus a **separately administered append-only witness** outside the repository's own control. A transparency-log approach such as [Sigstore Rekor](https://docs.sigstore.dev/logging/overview/) can provide an independently auditable log of signed public commitments; a separate monitor must retain and check signed checkpoints and consistency. A log entry alone does not prove the policy is globally latest, supply a trusted clock, or establish separate administration. Qualify the actual witness, authenticated freshness source, maximum allowed age, access controls, recovery and both partial-update directions; fail closed when any are unavailable or disagree. Do not put secrets or sensitive identity data into a public log.

An alternative is a transactional checkpoint store plus a second, independently controlled witness service. As an example of a checkpoint primitive, [Cloudflare R2 documents atomic conditional writes](https://developers.cloudflare.com/r2/reference/consistency/); conditional writes alone are not a rollback witness or trusted time source. Neither option has been selected, provisioned or tested for this project.

GitHub protected environments can be an additional operational control, but [GitHub documents that only one listed required reviewer must approve](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments#required-reviewers). They cannot alone enforce the selected two-owner policy-change threshold. Provider account identities, repository ID, membership, protections, actual policy, approval semantics and availability still require separate authenticated qualification.

## Exact-archive next step

Design a narrowly scoped publisher that binds the source commit, exact three package names and versions, archive digests and independently verified review/policy evidence, then preserves the same validated bytes through actual transmission. Treat source archive mutation, wrong or duplicate package, wrong commit, stale or revoked policy, partial publication, retry, npm provenance and registry readback as explicit test cases. Select and test the actual npm-compatible transfer and process-isolation boundary; neither a mutable-path preflight hash nor the in-memory fixture transport establishes that boundary. Changesets remains the version-intent coordinator. The existing release script and workflow stay disabled until production prerequisites and publication are separately authorized.

For eventual authenticated publication, evaluate [npm trusted publishing using OIDC](https://docs.npmjs.com/trusted-publishers/) on a supported hosted runner rather than assuming the existing long-lived token template is suitable. npm documents automatic provenance under its stated public-repository and public-package conditions. Its trusted-publisher configuration expires if its first publish is not completed within two days, so do not configure it during this local-only phase. Actual package bootstrap, ownership, OIDC permissions, provenance and registry readback remain unqualified.
