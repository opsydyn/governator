# M3a review-evidence contract and local verifier design

Status: implemented locally; the real GitHub provider remains separate. M2 is integrated into local main at `877b5c9`. This document does not configure a provider, grant approval or authorize publication.

## Intent

Prepare Governanator for the handoff's GitHub-authenticated reviewer evidence while preserving its current fail-closed release gate. M3a is a local, fixture-backed slice: exercise the shape and decision rules for exact candidate review, but do not represent a mock response or signed local document as an authenticated GitHub review. Real provider activation and its independent authority require a separate qualified integration.

Today `assessRelease` accepts simulated review only in demo mode and reports normal distributed changes as insufficient because trusted owner review is unavailable. The repository has no configured Git remote, GitHub reviewer/team mapping, protected-owner policy or observed authenticated provider. A review of a commit does not, on its own, prove approval of a subsequently produced tarball. GitHub permits review bodies to be edited; a digest found in a review body cannot yet be treated as an immutable approval of that digest.

## Approaches considered

1. **Local fixture verifier and provider boundary — recommended.** Develop pure, versioned inputs and deterministic checks against synthetic observations, with explicitly simulated outcomes. It lets us establish and test scope, lifecycle, freshness and role requirements without granting live authority. The cost is that ordinary releases remain blocked until a separately configured provider and binding mechanism are qualified.
2. **Connect directly to GitHub and enable the real gate now.** This would require an identified repository, authenticated read-only access, independently protected reviewer/role authority, current review-state handling, and a defensible immutable source-to-artifact attestation. Those prerequisites are absent; the current local-only work has not authorized account activation or remote writes.
3. **Accept a locally signed review as a GitHub approval.** A signature can prove possession of a local key, but not GitHub identity, current team membership or repository protections. An in-repository key list controlled by the proposed change also permits self-authorization. Reject this as a substitute for the handoff's trusted GitHub review.

## Scope and boundaries

- Add private, versioned schemas and a pure evaluator for **synthetic** review observations. Inputs include the host's expected candidate scope, an independently supplied synthetic authorization policy and a complete fixture observation set. Every result is explicitly marked `simulated` and cannot be passed as trusted human review to the existing normal release gate.
- Bind the expected scope to stable repository identity, pull request, source commit, package and version, baseline and exact candidate artifact digests, release input digest and the identities/digests of the release and reviewer authorization policies. Include candidate creation time and the evaluation clock. A record that binds only a source commit is source-only evidence, not exact-artifact approval.
- Derive reviewer identity and allowed roles from the fixture provider observation and separate policy, not from role names claimed in a review message. Mirror the existing rule: design-system-owner for distributed changes, plus API-owner for a major, without assuming that a particular username or team exists.
- Model approval, changes requested, dismissal, supersession and unknown/incomplete state. Missing pages, provider errors, revocation/membership ambiguity, unsupported history, future/stale/expired evidence and changed PR head fail closed. Do not assume GitHub's complete effective-review aggregation semantics until verified by the live adapter.
- Require exact scope equality and fresh time bounds. Fixture approval and artifact-binding observations must be no earlier than candidate creation and no later than the injected clock; require an unexpired interval of at most 24 hours. Test each boundary. A same-scope recheck can be idempotent during its validity window; durable one-use replay prevention is outside this slice. No cross-repository, cross-candidate or cross-policy substitution is accepted.
- Model artifact binding as an explicit synthetic claim, not a copied `approved` field, `authenticated: true` authority, editable GitHub review body or reusable capability. Even a fully matching fixture produces a simulated result. A real binding must eventually be independently authenticated; choosing and authenticating an immutable real binding remains an open M3 integration decision.
- Keep provider observations and any future verified host capability distinct from serialized reports, MCP snapshots and user-supplied JSON. No deserialized `{verified: true}` flag or claimed role list may upgrade trust. Existing normal release checks, public addon/protocol runtime boundary and read-only MCP behavior remain unchanged. `publishable=false`; publication, deployment and adoption remain unknown.
- The local slice makes no GitHub requests, reads no credentials, changes no remote settings, and creates no signing keys outside disposable test fixtures. It does not add or enable a publishing path.

## Acceptance

Tests should demonstrate valid **simulated** observations and fail closed for wrong repository/PR/source/package/version/baseline/candidate/input/policy, unknown or insufficiently authorized reviewers, missing roles, dismissed/changes-requested/superseded or incomplete reviews, partial pagination, provider unavailability, stale/future/expired evidence and cross-scope replay. Include tests that saved data or copied fixture output cannot enable the normal release gate, and that MCP continues to expose saved results only as observations. Use the existing Bun/Moon/TypeScript/Effect/oxlint/oxfmt/tsdown stack and preserve the addon budget.

Run the full local checks and package builds. Review the whole change independently, commit locally, fast-forward onto main and report directly observed checks and remaining gates. Regenerate source-bound dogfood reports and a new snapshot after the final committed source when qualifying MCP parity.

## Later integration, not M3a

A live GitHub provider needs a named host and repository, read-only authentication, pagination and rate/error handling, stable user IDs, current review and authorization state, an independently protected owner policy, and a qualified exact-artifact attestation. GitHub's list-reviews endpoint requires Pull requests: read; team membership may need additional organization permission. Branch protection and CODEOWNERS enforcement are repository administration concerns and cannot be inferred from a local file. Qualify provider freshness and review-body mutation semantics before treating any record as approval.
