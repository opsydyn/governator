# M3c exact-artifact attestation design

Status: **proposed**. This document designs a local, fixture-only verification slice. It does not approve a production trust model, enroll reviewers, connect GitHub, enable a release gate, or authorize publication. The reviewer-authority choice remains open.

## Intent and current state

Governanator needs eventual evidence that an authorized reviewer approved the precise release artifact. Its existing candidate check hashes the captured archive, checks inputs and source, reproduces the payload, and checks again for changes. The synthetic review evaluator already models repository, PR, commit, package and version, baseline and candidate digests, inputs, policy and time. Its results are simulated; the GitHub review reader returns unverified source observations. Normal release checks remain insufficient without trusted owner review.

A source review is not approval of a later tarball. A signature proves that a key signed bytes, not that a named human reviewed them, currently belongs to a GitHub team, or is authorized by an independent policy. A policy stored in or derived solely from the change under review must not establish its own authority.

## Approaches and recommendation

1. **Operator-managed policy and offline signed statement — recommended for the next local prototype.** An explicitly supplied fixture policy maps test public keys to fixture identities and roles. A verifier checks exact signed statement bytes and compares the full candidate scope. This gives a testable artifact-binding primitive without infrastructure, but an operator must independently manage real enrollment, role changes, revocation, policy freshness and key custody. It does not itself meet the handoff's trusted GitHub-review requirement.
2. **GitHub team policy and protected CI.** GitHub organization membership and repository protections can eventually inform reviewer authority; a separate authenticated artifact-binding mechanism is still needed. This aligns with the intended GitHub workflow, but requires a selected organization and repository, qualified access, effective-review semantics, current membership and independently verified protection configuration. CI provenance alone does not prove a human approved the exact artifact.
3. **Dedicated approval broker or GitHub App.** A service can authenticate reviewers and issue artifact-bound statements while centralizing policy, revocation and audit. It adds deployment, operating, availability and identity-provider obligations that are not justified for the offline slice.

The prototype assumes option 1 solely as an injected **fixture model**; the user has not yet chosen the eventual authority. Options 2 and 3 remain viable later providers. No local policy or key is to be accepted as production authority by implementing this design.

## Proposed local contract

- Add a private offline verifier with no default network, credential discovery, filesystem trust lookup, signing service, or publication path. Use the existing Bun/TypeScript/Moon/Effect/tsdown stack; test-generated keys and in-memory data only. The normal release checker, read-only MCP and public addon stay disconnected from the verifier.
- Use a narrowly profiled [DSSE envelope](https://github.com/secure-systems-lab/dsse/blob/master/protocol.md) containing an [in-toto Statement v1](https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md) and a versioned Governanator approval predicate. Bounds-check and decode the outer envelope, then verify the exact decoded payload bytes before parsing that payload; compare the signed payload and predicate types against fixed supported values. DSSE signs payload type and exact payload bytes; do not reserialize before signature verification. A key ID is a lookup hint, not evidence of identity or authorization. The existing `canonicalJson` function is for internal digests and must not silently become a signature canonicalization scheme.
- The subject binds the SHA-256 of the actual captured tarball bytes, represented as bare lowercase hex under in-toto `digest.sha256` and explicitly converted to the project's `sha256:` form for comparison. The predicate also binds explicit purpose and schema version; stable repository provider/host/numeric ID and PR; source commit; package name and version; candidate creation time; baseline, candidate and release-input digests; release-policy and reviewer-policy IDs and digests; reviewer fixture identity and review identifier; issued and expiry times. Compare each field against independently supplied expected scope; do not trust role or digest claims solely because they occur inside the statement. A caller-supplied expected digest is a comparison input, not proof that actual archive bytes were read; the existing candidate checker performs the independent archive rehash. Reject ambiguous duplicate JSON keys, unsafe IDs, invalid UTF-8, unsupported or unexpected fields, malformed encodings, excess data and unknown schemas or algorithms.
- Specify a single interoperable test signature profile before implementation: Ed25519 public keys in an explicitly encoded representation, DSSE pre-authentication encoding as specified, bounded envelope and payload sizes, one unambiguous signature per fixture statement, and immutable byte copies. Select Ed25519 from the verifier profile and fixture key, not an unsigned algorithm claim. Accept both standard and URL-safe base64 as required by DSSE. Add known-answer vectors, including an independent implementation or published DSSE vector. Domain and predicate types and the exact policy bytes to hash are defined in the implementation plan, not inferred from unsigned metadata.
- Supply expected scope, evaluation clock and policy fixture separately from the envelopes. A fixture policy maps a uniquely identified public-key fingerprint to a fixture actor, active/revoked state, allowed roles and repository scope. It is an input to a local experiment, not an independently protected trust anchor. Recompute its digest against the independently expected policy bytes and reject duplicate identities or key assignments, mismatches, unknown/revoked keys or missing role assignments. Verify and aggregate a bounded set of separately signed statements for the same expected scope, rejecting ambiguous duplicate signers or reviews; two distinct reviewers may contribute the two roles. Mirror current fixture semantics: distributed changes require a design-system owner and major changes also require an API owner; the same actor may satisfy both unless a future policy explicitly requires separation.
- Require canonical valid times, candidate creation no later than issuance, candidate age at evaluation no more than 24 hours, issuance no later than the supplied clock, expiry strictly later than the clock and issuance, and a maximum 24-hour statement interval. These are fixture checks; an injected clock and signed claimed time are not independent time evidence. A signed timestamp cannot prove that a signature preceded revocation.
- Reject cross-repository, PR, commit, candidate, package/version, baseline, input and policy substitution. Rechecking the same valid statement for the same exact scope is idempotent; no one-use or durable replay prevention is claimed. A nonce alone is not a replay store. A later release integration must select a protected current policy, prevent rollback using independently retained state, establish current revocation and role status, and revalidate exact artifact bytes at the point of release. Missing or stale protected state fails closed.
- Results explicitly distinguish signature validity and fixture-policy match from authorization: e.g. `assurance: "fixture-only"` and `status: "matched" | "insufficient_evidence"`. No copied JSON, flags, caller-provided roles, verified signature or result object can supply trusted reviewer capability to normal release or MCP paths. Do not present a matched fixture as authenticated GitHub review or real human approval.

## Acceptance and validation

Use disposable generated test keys and no real credentials. Cover valid exact scope; byte flips and payload-type substitution; wrong key, signature or algorithm; duplicate keys/identities/JSON properties; malformed or oversized payload; wrong repository, PR, source, archive, package, baseline, inputs and each policy ID and digest; unknown, inactive, revoked and rotated fixture keys; policy rollback/staleness using injected synthetic checkpoint and freshness fixtures, otherwise explicitly unknown rather than current; both role requirements with one and two signers; expiry, future and candidate-time bounds; and same-scope rechecks. Prove that changing the archive after any verification fails the existing candidate recheck.

Exercise the actual real-candidate release check and saved snapshot/MCP path with copied verifier results and forged flags: normal review remains insufficient, data stays unverified and no new approval tool is exposed. Run the full project checks, builds, addon/dependency guards and relevant focused tests; independent review should challenge the byte format, parser ambiguity, policy provenance and trust boundaries. On completion, commit and integrate locally on `main`; refresh source-bound dogfood/Storybook/MCP evidence. No live network, account access, push, publish or hosted activation.

## Later operational decisions

Before production authorization, decide the independent authority for reviewer enrollment and roles; how keys map to verified GitHub identities; who can update, revoke and recover policy or keys; trusted time and maximum policy age; rollback-resistant checkpoints; effective GitHub review and membership semantics; any author/reviewer separation rule; protected release execution and exact-byte handoff; and durable replay or one-use needs. These are not solved by DSSE or a signed policy digest. The [DSSE scope](https://github.com/secure-systems-lab/dsse/blob/master/governance/02-scope.md) leaves trust establishment and authorization outside the envelope protocol. [TUF's update model](https://theupdateframework.github.io/specification/v1.0.36/) illustrates that rollback and freeze checks require previously trusted state and time; an offline fixture cannot establish current revocation on its own.
