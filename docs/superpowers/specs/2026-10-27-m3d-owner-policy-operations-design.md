# M3d owner-policy operations design

Status: **proposed**. The user selected a repository-owner-managed reviewer policy and approved designing its operations. Thresholds and production infrastructure below are recommendations, not configured or approved operational settings. This document does not authorize implementation, real keys, account access, external resources, release-gate activation, push or publication.

## Why this phase

The M3c verifier checks signed candidate statements against caller-provided fixture policy bytes, checkpoint and clock. It reports `fixture-only`: those inputs do not prove that the policy is independently protected, current or associated with a real GitHub identity. The GitHub reader returns unverified review-list observations and does not establish stable repository identity, effective approval, current head or roles. The normal release gate remains insufficient.

The goal is to specify how an owner-controlled policy could eventually be administered without letting the change being reviewed choose its own approvers. First build a **local synthetic policy-lifecycle model**. It must exercise transitions and failure cases without creating an actual trust root or granting authority.

## Approaches

1. **Owner-controlled signed policy with independent trust anchor and checkpoint — recommended.** An independently selected root authorizes policy administration; signed policy revisions bind stable repository identity, reviewer keys and roles. A protected monotonic checkpoint detects rollback relative to its surviving trusted state. This supports local-first operation but needs separately qualified key custody, durable state, time and an authenticated freshness source.
2. **Policy only in the candidate repository.** Easy to edit and review, but a change that controls its own policy can authorize itself. Repository protection and administration may be bypassed or change; a local policy file does not prove that independent controls were active. Insufficient as the sole trust anchor.
3. **A hosted approval broker.** Can centralize authenticated identity, durable state and auditing, but adds service availability, account and operating obligations. A later separately authorized integration remains possible; no service is required to test lifecycle rules locally.

The user has chosen owner-managed authority. The signed-policy mechanism, two-person default and exact operational controls are proposed engineering choices, not facts about an existing organization.

## Trust boundaries and threat model

- The repository owner controls policy administration through independently protected administrator keys and explicitly configured authorization thresholds. The candidate source tree, PR contents, local user-supplied JSON, editable review bodies and M3c fixture results are untrusted and cannot enroll keys, choose roots, set the clock or reset checkpoints.
- Separate **policy administrators** from **release reviewers** as roles, even if the owner eventually appoints the same person to both. A reviewer signature proves possession of the associated key, not the person's GitHub identity, human intent or present policy authority. A GitHub source review is not an immutable approval of the tarball.
- A qualified host would obtain its trust root and prior checkpoint from a protected source outside the candidate's control, independently authenticate fresh policy state and time, and separately establish GitHub identity and effective source review. A root or checkpoint supplied by the same untrusted candidate is not authority. Protection of the running verifier and final publisher is also required; a process under attacker control cannot secure itself.
- Protect against unapproved enrollment/role changes, revoked or unknown keys, rollback to older policy, same-revision equivocation, expiration/freeze, key compromise, partial writes, concurrent updates and mismatched candidate or repository scope. A protected checkpoint detects regression relative to that checkpoint; it cannot prove it is the newest state, detect an unseen fork or survive adversarial rollback of its own backing store without an external witness or independently verified recovery.

## Proposed operating model

### Bootstrap and owner approvals

The repository owner selects the stable GitHub host and numeric repository identity, initial administrator public keys, key custody, policy ID and approval threshold through an independently authenticated out-of-band bootstrap. Initial root and initial checkpoint are installed as a deliberate operator action, not discovered from the checkout. Enrollment and administrative changes require the currently authorized administrator threshold; proposed default **two distinct administrators**, but the actual threshold and whether two independent owners exist are still a user decision. Do not silently fall back to one when the threshold cannot be met.

The root and reviewer policy have distinct purposes and versions. The root contains unique administrator identities, their unique public keys and the administrator threshold; that threshold authorizes reviewer-policy revisions. Count at most one verified signature per distinct administrator, even if an eventual representation permits more than one key per person. A root change, including adding/removing administrators or lowering the threshold, requires a sequential successor authorized by both the old and proposed new thresholds; reject ambiguous identity/key mappings, invalid thresholds and thresholds that cannot be met by eligible unique administrators. A normal root rotation follows the same old-and-new rule. Do not claim TUF compliance: this is a design inspired by [TUF's root update model](https://theupdateframework.github.io/specification/v1.0.36/), not an adopted implementation. A compromised threshold cannot authenticate its own recovery; freeze authorization and use independently verified out-of-band recovery or rebootstrap.

### Enrollment, role updates and key rotation

A policy revision binds policy ID, strictly increasing revision, stable provider/host/repository ID, validity bounds, predecessor digest, administrator-authorized actor-to-public-key fingerprints and allowed roles. The exact signed bytes and parsing profile must be defined before implementation. Every revision is authorized by the existing root/administrator policy and checked against an independently selected expected repository and prior checkpoint. Reject duplicate keys, actors or ambiguous assignments; keep release reviewer roles distinct from administrator roles. The first fixture profile permits one active key per actor, so rotation replaces that assignment without overlapping keys; the operational cost is temporary loss of approval until the new key is enrolled. A later multi-key profile would need explicit per-person deduplication and separate review.

For actual enrollment, the owner establishes the GitHub actor's stable numeric ID through a separately qualified authenticated provider flow and verifies possession of the proposed review signing key with a fresh, one-use, domain-separated challenge binding the key fingerprint, actor ID, repository, policy and challenge expiry. The challenge and authenticated identity observation must be linked by a trusted enrollment workflow; a signed claim of a GitHub ID or an unauthenticated profile lookup is insufficient. A key replacement is a new authorized revision; the first fixture profile removes the old key, while any eventual production overlap requires a separately designed policy. Key fingerprints are computed from verified key bytes, not trusted from unsigned labels.

Production use also needs a separately qualified GitHub source for current PR head, effective approval/dismissal, identity and repository scope. The M3b review list alone supplies none of those assurances. Verify that the effective GitHub source review and separately signed exact-artifact statement identify the same stable actor and match the independently expected repository, PR, head, review ID and current policy. The source review and artifact statement are distinct evidence; the source review alone does not approve the tarball. This design does not specify or activate the real GitHub flow.

### Revocation and recovery

An authenticated successor revision can revoke a reviewer key, remove a role or suspend authorization. At evaluation, an unknown, revoked, stale or ambiguously rotated key fails closed. A self-reported signature time does not prove signing preceded revocation; the conservative default rejects an approval from a currently revoked key unless a later design qualifies independent time and historical policy evidence. Admin/root key compromise or loss freezes affected authorization. Ordinary update requires valid prior checkpoint and root continuity; if either is missing or suspect it cannot proceed. Recovery is a separate, explicit path requiring independently authenticated out-of-band recovery authority, an auditable new root/policy, a new recovery epoch and a protected replacement checkpoint. That separate authority may rebootstrap when the original root is lost; the untrusted candidate or old backup cannot create the authority. If neither continuity nor independently verified recovery is available, remain unavailable. Restoring an old backup must not silently restore approval authority or lower the checkpoint.

### Checkpoints, time and freshness

A future protected checkpoint identifies the recovery epoch, root version and exact root digest, repository and policy ID, highest accepted revision and exact policy digest, and last trusted time or an independently protected equivalent time marker. Verify root/policy signatures, scope, predecessor continuity, authorization and time before advancing it. Reject lower revisions, same-version root or policy equivocation, unverified gaps or forks, expired or invalid state and clock rollback relative to the protected marker. Persist the accepted state atomically; use compare-and-swap or equivalent serialization for concurrent updates, and treat an uncertain partial write as unavailable until recovered from independently verified evidence.

A local clock and a signed expiration alone cannot establish that no newer revocation exists. Production qualification additionally requires a trustworthy clock and an independently authenticated freshness/update source with a policy-defined maximum age; missing, stale, unavailable, conflicting or rollback-suspect sources fail closed. Offline verification may say only that a signed policy matched its last trusted checkpoint within the stated time window, never that the policy is globally latest. A durable store does not itself protect against a privileged attacker restoring an old store; secure storage or an external witness and recovery process must be selected and qualified separately.

## Bounded next implementation: synthetic lifecycle only

After this design is approved, implement a private, deterministic in-memory lifecycle evaluator using disposable synthetic keys, state and clock. It accepts separately supplied fixture root/policy, a versioned synthetic store containing checkpoint and challenge state, and a proposed transition; outputs a versioned **fixture-only** result and either an atomic proposed store change or insufficient evidence. The caller-owned in-memory store models compare-and-swap against its supplied version and injected crash outcomes; stale versions cannot commit, a crash before commit changes neither checkpoint nor consumed challenges, and a completed commit changes both atomically. Recovery is a distinct transition using a separately injected synthetic recovery authorization and increments the epoch; a candidate cannot authorize its own reset. It does not pretend to provide real persistence, a trusted clock, GitHub identity, freshness, an operator policy or a recovery channel. Do not extend production release evaluation, the MCP approval surface or GitHub transport. No real keys, signing service, credential discovery, network or hosted storage.

Cover synthetic bootstrap with a separately injected root; threshold signatures, unique administrators, invalid/unsatisfiable thresholds and threshold reductions; policy enrollment/role change/rotation/revocation; root transitions authorized by old and new thresholds; stable repo and policy scope; exact signed bytes, duplicate JSON and invalid signatures; monotonic revisions, predecessor mismatch, same-version root and policy equivocation, gaps and fork; stale/future/expired time and protected-clock rollback; missing or rollback-suspect checkpoint; parallel update compare-and-swap; crash-before and crash-after commit; backup restore without rollback; compromised/lost root freeze and separately authorized synthetic rebootstrap; and challenge binding/replay using fixture identities. Each challenge is fresh, bounded, scoped and consumed atomically with the successful synthetic enrollment; replay, concurrent reuse and failed or interrupted commits have explicit tests. Challenge tests model an enrollment contract only and cannot establish an authenticated GitHub identity. Ensure matched lifecycle outputs and copied or forged fields cannot upgrade the real candidate check or saved MCP snapshot.

The implementation plan must pin exact signature and policy encodings, bounds, transition inputs and outputs, atomic model semantics and failure reasons before code. Test-driven development, full local checks/builds, independent review, fast-forward to local main and source-bound dogfood/Storybook/MCP verification remain required. Release authorization stays insufficient throughout.

## Production decisions and qualification still required

The owner must choose the administrator threshold and people, trusted root/key custody and backup, who can recover or revoke administrators, independently protected checkpoint storage, trusted clock, authenticated update/freshness and identity providers, recovery/witness process, audit retention, enrollment and reviewer-separation rules, GitHub effective-review semantics, maximum freshness interval, exact-byte release handoff and any one-use replay store. Identify the actual repository and secure the required GitHub permissions before requesting separate live access. No present fixture, local file, CI configuration or this design establishes any of these protections.
