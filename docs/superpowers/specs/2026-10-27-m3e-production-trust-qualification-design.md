# M3e production trust boundary and qualification design

Status: **proposed qualification design**, not a production authorization decision. The user selected a repository-owner-managed reviewer policy and at least two independent owner approvals for changes to it. Actual owners, repository, key custody, state/freshness provider and recovery authority are not yet selected or qualified. No real key, identity, credential, GitHub connection, release capability or external resource is created by this document.

## Purpose and current evidence

Define what must be true, who supplies it, and what evidence would demonstrate it before an authenticated GitHub reviewer and an exact-artifact approval could affect the normal release gate. Make the next real-world work a bounded qualification, rather than another fixture-only layer. The work described here is local planning; actual devices, accounts, repositories and remote resources require separate explicit authorization.

At the time of this assessment, local `main` contains the M3b unverified review reader, M3c fixture-only exact-artifact verifier and M3d fixture-only policy lifecycle. The normal release check still reports trusted owner review unavailable, and saved MCP data stays unverified. The checkout has no configured Git remote. The checked-in release workflow is disabled and manual-only; its existence does not prove hosted protection. The candidate check rehashes local tarball bytes during validation, but that is not proof of what a future publisher uploads. See [M3b](../../m3b-verification.md), [M3c](../../m3c-verification.md), [M3d](../../m3d-verification.md), [release candidates](../../release-candidates.md) and [releasing](../../releasing.md).

A source review, a reviewer key signature, the owner policy, freshness and the artifact handed to a publisher are separate facts. Missing, stale, conflicting or unqualified evidence keeps normal review insufficient. No fixture output or JSON field can cross that trust boundary.

## Candidate architecture and alternatives

- **Recommended evaluation path:** two independently controlled owner signing keys and a separately protected owner-policy root; a separately qualified rollback witness and authenticated freshness/time source; a read-only GitHub identity/review adapter; and an exact-artifact approval verified at the protected release boundary. This is a target to qualify, not a configured solution. The user's pending custody choice determines whether hardware backing is required.
- **Hardware key compatible with raw Ed25519/DSSE:** retain the current fixture signature profile only if an independently qualified device and host adapter can sign the exact DSSE pre-authentication bytes, export the expected public key, and enforce the desired human-presence and custody policy. Do not assume any particular token, firmware, middleware, PIN/touch setting or OS supports it. A successful 64-byte cryptographic signature proves key use; it does not by itself prove a distinct human, hardware provenance or presence policy.
- **FIDO2/WebAuthn or OpenSSH security-key profile:** design and verify the complete assertion protocol, including its signed context and any required user-presence/user-verification flags. These signatures are not automatically the raw Ed25519-over-DSSE signature accepted by the current fixture verifier. Do not strip context or treat the formats as equivalent. This needs a separately approved verification profile and a real-device qualification.
- **Independent software keys:** operationally simpler but increase key-copy and compromise risks. This is an alternative only if the user selects it and independent custody, authentication, recovery and verification are qualified; no fallback is automatic.

[OpenSSH security-key protocol](https://github.com/openssh/openssh-portable/blob/master/PROTOCOL.u2f) and [WebAuthn](https://www.w3.org/TR/webauthn-3/) define additional signed context. [Yubico's PIV algorithm table](https://docs.yubico.com/hardware/yubikey/yk-tech-manual/yk5-apps-piv.html) illustrates that Ed25519 availability varies with firmware; it is not a recommendation or proof that any attached device works.

## Qualification gates and required evidence

All gates below are **unqualified**. Passing local synthetic tests is useful test evidence but cannot close a gate. An operator records the actual selected component, version, scope, date, test procedure, result, reviewer and retained artifact for each qualification. Evidence containing credentials or private keys must not be retained.

The [TUF specification](https://theupdateframework.github.io/specification/v1.0.36/) illustrates separately bootstrapped trust, threshold root rotation, persisted versions and expiry checks. A protected checkpoint detects rollback relative to its surviving witness; it cannot alone prove no newer policy exists or that its own storage was not rolled back. This project does not implement or claim TUF compliance.

The current fixture policy requires a design-system owner for a distributed change and an API owner as well for a major; one reviewer may hold both roles. The two-independent-owner threshold selected by the user governs changes to reviewer policy, not automatically every artifact approval. A production profile must independently validate the applicable role requirements and all decision inputs, or explicitly specify and qualify a stronger equivalent.

The selected protected runner must also establish integrity and independent control of the verifier, policy decision logic and expected scope; a candidate-controlled verifier or attacker-controlled process cannot secure itself. A real state/witness design must specify authenticated witness identity, equivocation handling, write ordering and fail-closed reconciliation for a crash between store and witness writes in either direction. Qualification must exercise those partial advances and recovery rather than infer atomicity from the fixture model.

GitHub pages are not an atomic snapshot. The production design must bound evidence age and revalidate effective review, dismissal, head and policy at the final decision and artifact handoff; qualify races between those checks and define when a change invalidates the decision. If a consistent, current view cannot be established, remain insufficient rather than infer approval from a completed listing.

## Local qualification completed for this design

The current repository was inspected without accessing accounts or keys. Its GitHub review reader has no qualified real transport, the policy and signing packages are fixture-only, normal release review is insufficient, the release workflow is disabled, and `git remote` listed no configured remote. Existing local tests exercise synthetic two-owner signatures, cross-epoch challenge replay, state witness rollback and normal-release/MCP isolation. These establish no claim about an actual device, person, organization, GitHub configuration, production clock or state store. No new production or device test has run.

## Operator qualification sequence, when separately authorized

1. **Choose scope and owners:** identify the repository by host and numeric ID, two independent owner principals, security/recovery owner and agreed identity/custody policy. Confirm the selected key approach and actual device/middleware compatibility before enrolling anything. Ownership or account details are not guessed.
2. **Choose and threat-model real substrates:** explicitly select checkpoint/challenge storage, independent witness, authenticated freshness source, clock and recovery channel. Specify who controls each, threat assumptions, failure modes, audit retention and maximum freshness interval. A single user-controlled local file plus the same user's clock is not rollback-resistant evidence.
3. **Prepare a disposable, isolated interoperability qualification:** with separate authorization, exercise two test identities/devices and disposable credentials against the selected signing and identity profiles; capture public evidence and negative tests. No production keys or policy activation. For a hardware profile, verify exact bytes, real device behavior and format end-to-end; no conversion may discard protocol semantics.
4. **Qualify policy and GitHub reads:** only after an explicit repository/access authorization, test authenticated actor-to-key binding, current review semantics, denied/unavailable paths, protections and freshness. GitHub access is read-only, with permissions and endpoints reviewed for side effects; no repository rules are modified by this phase.
5. **Qualify protected artifact custody:** demonstrate the proposed release process revalidates current authority and exact bytes at the point of handoff, with tamper and rollback negatives. Registry publication, CI activation, real owner enrollment and normal-release gate enablement remain independent decisions and are not implied by a successful qualification.

Each stage stops with its evidence marked `pass`, `fail` or `unavailable`; unavailable or expired evidence is not a pass. Tests performed on fixtures, a local mock, a real device, an authenticated GitHub API, a hosted runner and a registry each remain distinct evidence classes.

## Recommended next bounded work

Once the owner and repository identities and key-custody choice are available, produce a concrete qualification protocol for the chosen signer and state/witness substrate, with disposable test credentials and explicit no-mutation boundaries. First prove the selected signing interface against the existing DSSE byte profile or design a separate security-key assertion verifier if needed. Do not claim hardware compatibility, operate real accounts, enroll real keys, or enable a release until those actions have separately been authorized and qualified.
