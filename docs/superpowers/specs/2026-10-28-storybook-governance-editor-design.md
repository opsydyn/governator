# Storybook governance metadata editor

Status: **proposed design**. The user chose descriptive tags and governance metadata for the 0.1.0 editor and approved the registry-backed approach. This document describes the proposed implementation for review; it does not assert that the editor or its qualification already exists.

## Intent and boundaries

A maintainer using a local React/Vite Storybook can inspect and edit a selected component's declared governance metadata in the repository's canonical registry, alongside the existing descriptive tag editor. The fields are declarations for normal version-control review, not verified decisions. Storybook must remain useful when the editor or report is absent. Static builds and non-opted-in development servers remain read-only. No hosted authoring, registry publication, GitHub integration, approvals, evidence creation or policy bypass is included.

## Approaches

1. **Extend the local opt-in Storybook authoring adapter to update the canonical registry (chosen).** Maintainers work in one place and keep the registry authoritative. This adds a Node-only write boundary and requires careful identity, validation and conflict handling.
2. **Separate registry editor outside Storybook.** This isolates the writer but leaves the approved in-Storybook experience incomplete.
3. **Store governance fields in CSF parameters.** This duplicates canonical data and conflicts with the handoff, so it is excluded.

## Experience

The Governance panel offers a distinct declared-metadata editor when the local adapter is configured and the selected story has an unambiguous literal component ID matching exactly one registry entry. It exposes name, owners, lifecycle, source, stories, package, export path, contract version, optional package version, replacement ID, documentation URL and Figma URL. The stable component ID is displayed but is not edited here; creating, deleting or renaming component IDs is outside this slice. Existing tags remain independently editable in their CSF file. Each editor has its own save, errors and conflict/reload state; no claim of an atomic transaction across registry and story files is made.

Inputs use accessible labels, keyboard operation and clear validation messages. A save changes a local declaration only. Display a persistent notice after a successful metadata save that the currently displayed report is a previous snapshot and must be regenerated and reloaded; do not imply that the saved declaration has passed transition policy, readiness, compatibility or release gates. The report remains explicitly identified as a snapshot, and invalidate current-result claims across the whole report, readiness markers and sidebar filter when the source-consistency check fails; clear restrictive filters so stories remain visible. A page reload cannot by itself establish that a report was regenerated: compare the report commit against the local repository commit only when the registry bytes also match the tracked file at that commit; otherwise keep the report visibly unverified. This is a local source-consistency check, not authentication of the report producer. If the adapter cannot establish both conditions, it must fail closed. Static and non-opted-in Storybooks cannot perform this local comparison and must label the report as a snapshot without claiming a live source match. Evidence, decisions, publication, deployment, approvals and reviewer policy are not editable.

## Storage and validation

Configuration explicitly identifies the repository root and registry path for this local adapter; do not infer write authority from a browser-supplied path, story title or report. Server-side configuration is constrained to the intended repository, and the browser supplies the selected story identity, component ID, expected registry revision and allowed field values. Reject ambiguous, missing, dynamic or mismatched identity. Independently derive and revalidate the story-to-component association on the server from current index and source, including at save time; a client-provided map or ID alone cannot authorize a write. Require the selected story source to appear in the existing registry record. Recheck the association if the index or source changes during the save.

Read the current registry with the project's existing YAML semantics and validate the complete proposed registry using the same authoritative component schema and registry invariants as the CLI, including unique IDs and story identities, safe relative paths, semantic versions, deprecated replacement requirements, and valid acyclic replacement references. Apply the CLI project loader’s canonical contained regular-file checks to source and story paths; reject the save when those checks cannot be established. Validate all changed values server-side and reject unknown fields. Preserve unrelated records, fields, comments, formatting and line endings; reject duplicate keys, aliases or other unsupported or ambiguous YAML forms rather than rewriting them lossily. Preserve comments and quoting where the supported parser can do so; fail closed otherwise. File paths and URLs are declarations, not proof that external destinations are trusted. A syntactically valid lifecycle change is still subject to policy evaluation and review.

The write endpoint is development-only, same-origin and loopback-only, as with the existing tag writer. Bound request and file sizes, constrain paths to a configured canonical regular file with no symlink traversal, reject malformed input, use an optimistic content revision and a per-file in-process write queue, then recheck before atomic replacement. Surface conflict and recovery instructions. Independent processes are not locked; document this limitation. The addon browser bundle must retain the Storybook-only peer and no Node, Effect, CLI or engine runtime dependency. If validation uses shared core code, isolate it in the Node-only authoring build and qualify the packed distribution; do not silently duplicate or weaken registry semantics.

## Verification and rollout

Test accepted edits and round trips, exact source preservation, all field constraints and registry invariants, unknown IDs, mapping mismatches, malformed and unsupported YAML, path/symlink and origin restrictions, concurrent edits and conflict recovery, absence of writes in static/non-opt-in mode, report invalidation behavior, accessible UI states and unchanged tag editing. Exercise a real local Storybook and independently packed npm and strict-peer pnpm consumers using the qualified Storybook 10.6.4 combination. Run full workspace checks, addon boundary/bundle budget, Storybook and docs builds; report any limits such as gzip headroom and deferred human validation. Document setup, review workflow, declared-versus-evaluated semantics and unsupported cases. Keep changes local, commit and fast-forward local main after checks, and recommend the next release-readiness item. Do not push, publish or activate hosted workflows without further authorization.
